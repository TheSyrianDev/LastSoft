Part LH · the harness

LastHarness

The part that runs the turn. Give it a model and a goal and it loops: build the prompt, call the provider, run the tools the permission rule allows, write what is worth keeping, stop when the goal is met.

LastHarness is the harness inside Last AI, published as its own repository: main is the studio on its own, omarchy is the edition that follows the desktop's theme. It is the same code as Last AI, not a separate download.

What is in it

PieceResponsibility
CoreState, the turn loop, the HTTP API on loopback, the token the clients present.
ClientsA terminal app, a desktop app, paired browser pages and messaging channels, all thin.
Provider layerLocal runtimes and cloud APIs behind one shape. Keys by reference, never stored in config.
ToolsFile reads and writes, shell, search, MCP servers, each behind a tiered permission rule.
MemoryMarkdown notes plus a database index. Files are the truth; the index is a cache.
LearningRules, style and skills as separate prompt blocks, versioned, logged when applied.
TeamDepartments and role workers as Markdown, the plan/run/check loop, nesting, autonomy.
SpendA ledger of what each provider call cost, priced from your own table.

What is deliberately not in it

  • No downloader. It does not fetch models; Model-Downloader does that, and the studio calls it.
  • No inference engine. It talks to a server you point it at. Today that is llama-swap, llama.cpp, Ollama, LM Studio, or a cloud API.
  • No account, no relay, no sync. The only network calls are the ones a request implies.

Because of that, the harness runs against any OpenAI-compatible server. If you already serve a model with something else, the harness is the whole product you need.

The turn loop

  1. Prompt assembly. Base prompt first, then the learned blocks (rules, style, skills) in order, then the memory this task needs. The base prompt is not rewritten; learned text is appended and every version is kept.
  2. Provider call. One request per step, to the model the worker is assigned. Streaming to whichever client asked.
  3. Tool gate. Every tool call passes the rule for its tier: free read, ask-once write, always-ask for anything that leaves the machine or destroys data.
  4. Effects and spend. Tool results are appended; provider cost lands in the ledger; the machine lock is taken when a job needs the GPU alone.
  5. Check and continue. The step is checked against its goal. Failures retry, move to another model, get done by the lead, or come back to you with the attempts.

Using it

Build the core and the terminal client without the desktop app: 

cargo build --release -p lh-core -p lh-tui

./target/release/lai setup
./target/release/lastaid      # 127.0.0.1:7842, token in $XDG_RUNTIME_DIR/lastai/token
./target/release/lai

Point a client at another core with --url and --token-file. The core takes flags that override config.toml, which is how a test instance runs on a temp store: 

scripts/smoke-headless.sh      # starts lhd on a temp store, exercises the HTTP API

Prompt blocks, in order

BaseThe harness's own instructions for the loop. Never edited by learning.
RulesHabits you approved. Numbered, removable one at a time.
StyleHow you want answers written. A separate block, not a rewrite of the base.
SkillsProcedures the worker can follow, loaded on demand.
MemoryNotes relevant to this task, retrieved from Markdown files.

Everything applied without asking is recorded in the activity log, so an unexpected answer can be traced to the block that shaped it.

Boundaries worth stating

  • The core binds to loopback only. Remote access is a paired browser or a channel you switched on, not an open port.
  • MCP servers do nothing until you approve them; a project folder may only bring its own if you lh trust it.
  • Team workers can share a model or split across models, and steps on one model are grouped so nothing loads twice for nothing.
