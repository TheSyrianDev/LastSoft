Part LE · v0.1.0, in development

LastEngine

Inference without a framework under it. Rust, a clean room, and a target that is deliberately small: mixture-of-experts models on the kind of GPU most people actually have: a 4 GB laptop card first.

Measured on Linux x86_64 with an NVIDIA card (sm_86, RTX 3050 Laptop). The Windows build compiles in CI but has not run a model on a Windows GPU. Treat it as an engine to watch, not the engine behind the studio yet. Last AI talks to llama.cpp-family servers today.

One trait, several backends

Everything is written against a single backend trait, so the rest of the engine (model loading, sampling, the server, benchmarks) never learns which hardware it is on. At startup the engine probes the machine and picks the strongest backend that can actually work.

BackendState
CUDAFirst backend. Kernels are compiled from source at runtime through NVRTC, so the build follows the card.
CPUSecond backend, and the fallback when no GPU path works.
VulkanPlanned, from the same kernels through GLSL to SPIR-V. Reaches AMD and Intel cards.
ROCmPlanned, alongside Vulkan for AMD.
MetalPlanned, for Apple silicon.

Probe first, then decide

lastengine probe          # one JSON object: GPU, VRAM, RAM, backends
lastengine probe --json   # the same, explicitly

The probe is the honest part of the design: before a model is loaded the engine knows how much memory it has, what the GPU reports, and which backends respond. The studio uses the same answer to tell you whether a model fits, is tight, or is too big. On Windows the RAM fields come back null today.

The server speaks llama.cpp's dialect

The engine runs as a server, so anything that speaks OpenAI chat to a local server can use it, including the harness. Responses carry a llama.cpp-style timings object, and there are endpoints for watching work as it happens:

GET /statsModel info, uptime, active requests, totals including prefill and decode tok/s, average time to first token, last request.
GET /stats/requests?limit=NThe last 200 requests.
timingsOn every chat response: prompt_n/prompt_ms/prompt_per_second, the same for predicted tokens, cache_n, time_to_first_token_ms.

The rules that keep it honest

  • Clean room. No code from the previous engine tree; that tree is kept only as a benchmark baseline binary.
  • Ideas have sources. Anything borrowed conceptually comes from a README, a paper or a file-format spec, and the module's header comment says which.
  • Benchmark everything, drop what loses. A technique stays only if it wins on this hardware; the results live in the repository's benchmark notes.
  • Licences travel. Any third-party code keeps its notice and is listed in NOTICE.

Where it goes next

  1. Batched decode, because the backend lock serializes requests today, one generation at a time.
  2. Expert caching for MoE models, which is the whole reason for the small-card target.
  3. Vulkan, then Metal, behind the same trait.
  4. An embeddable library crate next to the server, so the harness can link the engine instead of starting it.
